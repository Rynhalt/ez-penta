# UK cultural extension: run instructions

Open `data_ready/generate_dataset2_uk.ipynb` using Colab → File → Upload notebook.
Choose Runtime → Change runtime type → GPU (T4 or better), then Runtime → Run all.
The notebook embeds the shared Python code; no repository push or clone is necessary.

1. Set `SOURCE_DB` to the existing **Dataset2 prompt database** on Drive. Default:
   `/content/drive/MyDrive/ez-penta/dataset2.sqlite3`. If your file is named
   `dataset2_partial.sqlite3`, change that setting. A response `results.sqlite3`
   or an AnswerCarefully database is not the input for this extension.
2. Authorize the Drive mount. The public Qwen generator does not require Tiny Aya's gated HF credentials.
3. Keep the default `SEED_LIMIT = None` to process the full existing seed set.
   Results go directly under `MyDrive/ez-penta/dataset2_uk/`.
4. Identical reruns reuse checkpoints. An optional limited run is available by setting
   `SEED_LIMIT = 5`; its outputs go separately under `dataset2_uk/pilot/`.

## What is generated

Existing neutral JA/EN requests are adapted together to UK context. The generator
reuses existing harmful and twin requests, the original source IDs, and the original
analysis/tune/heldout splits. It copies neutral prompts and their IDs unchanged.
Fiction, roleplay and refusal-suppression definitions come directly from
`dataset2v2.ipynb`; `build_uk_notebooks.py` extracts them when rebuilding notebooks.
The notebook uses the existing `rewrite_helpers.run_rewrites` batching, OOM fallback,
input/configuration identities, and checkpoint persistence.

By default mixed-language variants are included, matching the existing Dataset2
layout: at most 28 UK prompts per seed plus up to 28 copied neutral prompts. For
320 source seeds, at most 8,960 new UK prompts; actual coverage depends on existing
twins, generation completion and parse validity. Set `INCLUDE_MIXED = False` for
JA/EN only (16 UK plus up to 16 neutral per seed).

The original Dataset2 seeds were generated by Qwen. This notebook does not import
AnswerCarefully or generate new independent seeds. It does not create a fresh test
set: historical seed exposure and splits carry over.

## Files on Drive

- `dataset2.sqlite3`: prompts, seeds, seed_texts, UK technique_outputs, prompts_wide,
  and generation_info. Neutral technique text remains in the copied prompts and
  wide table; the original source database hash records its provenance.
- `dataset2.manifest.json`: source/output hashes, settings, seed inventory and counts.
- `prompts.csv`: full prompt table for inspection.
- `dataset2_selection.json`: original source IDs and split assignments.
- `dataset2_uk_bases_checkpoint.jsonl`, `dataset2_techniques_checkpoint.jsonl`:
  raw generation outputs, truncation/errors and input identities; sibling settings JSONs.
- `base_generation_review.csv`, `technique_generation_review.csv`,
  `generation_review.csv`: accepted/missing/malformed/truncated generation inventory.
- `run_config.json`, `environment.txt`: pinned generator commit, full templates,
  dependency versions and settings. Changing settings requires a new output folder.

Truncated, empty, or invalid JSON outputs do not become evaluation prompts.
Unsuccessful jobs remain visible. Restarting identical settings does not retry a
completed-but-malformed or truncated generation; inspect the checkpoint and use a
new output folder with corrected settings for such a rerun. Generated semantic
and cultural equivalence remains **provisional**, even when structural checks pass.
The source's expected-behavior labels are preserved, not newly validated.

## Evaluate the original and trained HF models

Open `eval/eval_dataset2_uk.ipynb` in a fresh Colab GPU runtime with an HF account
that can access Tiny Aya. The default is `COHORT = 'full'` and
`MODELS = ['baseline', 'restricted']`. Add `broad` if needed, or choose restricted
only to inspect that model (a before/after comparison needs baseline too).

Keep the UK dataset and manifest under `ROOT`. Set `DRIVE_PROJECT_DIR` to the
project folder containing `post_train_2`, or set an exact adapter folder in
`ADAPTER_OVERRIDES`. Automatic lookup follows the supplied `eval_restricted.ipynb`:
search `post_train_2/notebooks`, `notebooks/combined`, `view_evals`, and project roots
for `pipeline4_restricted_adapter`, `pipeline4_full_adapter`, or `pipeline4_adapters.zip`.
ZIP extraction uses local runtime storage and rejects path traversal.

Use Colab Secrets `HF_TOKEN` with notebook access enabled, or an existing HF login.
The notebook now uses original HF weights and `PeftModel.from_pretrained(...).
merge_and_unload()`; this replaces the earlier GGUF-only UK evaluator. Baseline
and trained arms use the same resolved base revision and precision. Select the
actual training base revision in `MODEL_REVISION` when known; a newly resolved
revision alone does not establish historical training-revision parity.

Like the supplied reference notebooks, decoding is greedy, with 512 answer tokens
and 64 guard tokens. Differences are deliberate and saved: one prompt per batch
for memory/checkpoint reliability; bf16 on supported GPUs and fp16 on T4; full
prompt inputs instead of silently truncating to 1,024 tokens; truncation status
tracked explicitly; the shared scorer also records prompt safety independently.
These settings do not imply exact reproduction of earlier 228-prompt results.

Each model runs on the same UK+neutral prompt inventory. Models are released
before loading the HF Qwen3Guard. Both baseline and trained responses must come
from this HF protocol; historical GGUF answers are not mixed into the comparison.

Outputs:

`MyDrive/ez-penta/dataset2_uk/[pilot/]evaluation_hf/<dataset hash>/<settings hash>/`

- `<model>/part1/observations.csv`, `results.sqlite3`, `comparisons.csv`,
  `answers_current.jsonl`, `scores_current.jsonl`, `run_metadata.json`.
- Per-model durable `answers.jsonl` and `scores.jsonl` journals, raw guard replies,
  input/output token IDs, adapter file hashes and execution status/traceback files.
- `baseline_answers.jsonl`, `restricted_answers.jsonl` (and optionally broad):
  compatibility views with `id`, `model`, `language`, `label`, `pair_id`, and
  `pair_bucket` alongside the Dataset2 columns. These contain the new UK cohort,
  not the historical 228-prompt evaluation inventory.
- `before_after.csv`: paired transitions, known denominators and descriptive
  confidence intervals bootstrapped over source seeds, separated by original split,
  culture, language and request kind. Repeated variants are not treated as independent
  trials; automatic twin refusals are not asserted to be validated over-refusals.
- `settings.json`, `environment.txt`, `gpu.txt`; resolved model/guard commits in
  the enclosing dataset folder's `model_revisions.json`. No tokens are written.

Identical runs resume compatible answers and scores. Different model/settings hashes
use separate directories. No Part 2 or historical two-shard merger is required.
Keep review/approval fields provisional and audit historical seed exposure before
claiming fresh heldout generalization.

## Maintenance and verification

After changing shared code or templates, rebuild embedded assets:

```sh
python3 data_ready/build_uk_notebooks.py
python3 -m unittest discover -s tests -p test_dataset2_uk.py -v
```

Tests exercise source preservation, split preservation, parser/truncation rejection,
content-sensitive IDs, the real SQLite validator, and the shared comparison/export
path on synthetic fixtures. They do not constitute a Qwen or Colab GPU run.
No human approvals or CircuitKIT execution inputs are created by these notebooks.

Local verification (2026-11-12): 12 tests passed across the UK extension, original
Dataset2 validation, and shared analysis. Both notebooks' embedded helper snapshots
were checked against the current source. The real source pilot loads five **analysis**
seeds, 116 neutral prompts and ten existing harmful/twin bilingual requests. The pilot
selection is analysis-only; the full run preserves all original splits. Real Qwen/Colab
GPU execution has not yet been performed for these new notebooks.

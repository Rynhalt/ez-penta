Dataset2 implementation and technical evidence (2026-11-07)
=========================================================

Current default update: both notebooks now use the earlier GGUF/llama.cpp workflow (Aya Q4_K_M and guard Q8_0), with independent GGUF output directories. Earlier fp16 details below document the prior implementation and the optional future HF likelihood path.

Repository audit and reuse
--------------------------

The existing `eval/eval_dataset2.ipynb` already loads Tiny Aya in fp16, applies its chat template once, decodes greedily, releases Aya before judging, calls AuditKIT on precomputed answers, and exports SQLite through local storage. Its staged subsets and weak cache identity do not satisfy independent parallel full-shard execution. `evaluate_answercarefully.py`, `guard_judge.py`, `answercarefully_dataset.py`, `chat.py`, and `local_server.py` were inspected. Their local llama.cpp process/HTTP path is useful for the existing macOS workflow but unnecessary for the Hugging Face Colab workflow. It remains unchanged.

The new modules reuse `eval.checkpoints.config_id/file_sha256`, `guard_judge.parse_guard`, `eval.scoring.guard_messages`, AuditKIT's `Sample`, `RunConfig`, `GuardJudge`, and precomputed model. Existing `eval.analysis` assumes the earlier source/variant/language key, so Dataset2 gets a separate analysis module keyed by original prompt IDs and full condition metadata. Existing helper modules and unrelated worktree changes are preserved.

Sharding
--------

`dataset2_data.make_manifest` groups seeds by category and original split, sorts by severity, mixed direction, retained count and SHA256([42,seed_id]), then pairs adjacent seeds. An ordered subset-sum dynamic program chooses one seed from every pair, minimizing absolute workload imbalance with deterministic ordered first-path tie breaking. No random generator, solver, row order or Python hash randomization affects the assignment. The checked-in CSV is authoritative; both notebooks verify its JSON fingerprint, source database SHA256 and deterministic reconstruction before inference.

Each shard has exactly 160 seeds / 10,592 prompts. Each category contributes 16 seeds per shard. Each category contributes 8 analysis / 5 tune / 3 heldout seeds per shard. Totals per shard are 80 analysis / 50 tune / 30 heldout. Severity counts are 76/77 borderline and 84/83 clear. Mixed-direction seed counts are 84/76 versus 76/84; this is a workload allocation, not a treatment. Exact global workload and category/split seed balance take precedence over exact condition counts. `validate_dataset2` exports the full balance table.

Scientific policy
-----------------

All 21,184 retained prompts remain generation eligible. The dataset has 498 identical original/twin control pairs (119 seeds), 2,943 duplicate final-text excess rows and 5,696 absent design variants. Incomplete seeds are retained; absent variants are never synthesized. Original labels, text and partitions remain unchanged. Identical original/twin conditions cannot support an expected behavioral contrast. Their generations remain useful for consistency inspection.

Potential harmfulness-label errors, twin task drift, cultural equivalence, rewrite fidelity and borderline expectations require human review. Every generated expectation remains unvalidated by default. Script/language mismatch and phrase-based refusal checks are explicitly heuristics. Expected-behavior correctness, attack success and over-refusal therefore remain unknown until validated expectations and human outcome rules exist; response Unsafe rate and guard Refusal rate are separately reported automated measurements. Raw observations, errors, unknowns and denominators survive all exports. Do not use heldout outcomes to tune the generator, judge, parser or selection policy. Manual-inspection CSV contains blank human fields and supports uncertain labels; no human review is claimed.

Future CircuitKIT readiness (no attribution implemented)
--------------------------------------------------------

Official [CircuitKIT README](https://github.com/Lexsi-Labs/CircuitKIT/blob/main/README.md) documents Tiny Aya/Cohere-family support; [task documentation](https://circuitkit.lexsi.ai/user-guide/tasks/) describes paired loaders and metrics; [EAP documentation](https://circuitkit.lexsi.ai/algorithms/eap/) describes clean/corrupted forward passes and scalar attribution objectives. Compatibility of the specific Water checkpoint, TransformerLens conversion, attention hooks and installed dependencies still requires forward/logit parity and bounded attribution tests. It is not proved merely by family support.

Start with manually validated same-language prompt pairs and refusal/compliance continuations, preserving seed IDs, template boundaries and exact token IDs. Match token positions or explicitly design alignment before crossing languages or sequence lengths. A single-token logit difference fits conventional objectives relatively directly after backend compatibility checks. Multi-token sequence likelihood requires differentiable teacher-forced computation, possibly separate continuation passes, masking and gradient accumulation through the attribution loop. The optional scoring module uses inference mode and is a diagnostic, not a differentiable attribution metric. A custom TaskSpec alone does not implement that machinery. Future work must validate EAP/EAP-IG scores with activation patching, random/negative controls and causal faithfulness checks. No model training, steering, pruning or CircuitKIT execution belongs to this delivery.

Qwen's pinned files were readable: qwen3 architecture, 32,768 positions, bf16 checkpoint default, EOS IDs [151645,151643], and a dedicated 4,058-character moderation template. This access limitation affects real Tiny Aya model/tokenizer validation, not dataset, sharding, checkpoint, merge or fixture notebook verification.

A tiny random Cohere2 model verifies chunked teacher-forced continuation scores against a full-forward reference (absolute tolerance 1e-5). Tensor-level generation tests verify exact token counts, attention-mask forwarding and EOS-at-cap termination. Both notebooks pass nbformat schema checks and execute every pipeline cell with fixtures. These checks do not claim inference with actual Tiny Aya weights or a GPU.

Self-contained setup uses notebook metadata for the compressed asset archive, keeping every code cell below 15 KB. GGUF implementation evidence (current default)
---------------------------------------------

The original `notebooks/answercarefully_colab.ipynb` pins llama.cpp `d1044bc82712fbf08996080bef6298b24a27e9c7` and downloads local GGUF files. Dataset2 now reuses its `local_server.py` process ownership and `colab_build_cache.py` GPU-specific build cache. The launcher adds an optional context-size argument with its historical default retained; Dataset2 explicitly requests 8192 tokens, one slot, full GPU offload and no context shifting. Guard launch retains `--no-prefill-assistant`.

Public Hub metadata resolved Aya GGUF revision `bfe7fe10f8f206192097eeedcecdfbb1a11f9ca7` and guard GGUF revision `be4e562404e1bd6d6e01bed9c5fcf1ddb4a6c6aa`. Publisher LFS hashes and byte sizes are pinned in `dataset2_gguf.MODEL_SPECS`. Both actual file endpoints returned HTTP 206 and the `GGUF` magic bytes without credentials in bounded four-byte access checks; full model weights were not downloaded locally.

The pinned [llama-server API](https://github.com/ggml-org/llama.cpp/blob/d1044bc82712fbf08996080bef6298b24a27e9c7/tools/server/README.md) and [server implementation](https://github.com/ggml-org/llama.cpp/blob/d1044bc82712fbf08996080bef6298b24a27e9c7/tools/server/server-context.cpp) verify `/props`, `/apply-template`, `/tokenize` and `/completion`. Template application uses the same chat parser/server settings as chat completions. Dataset2 tokenizes that rendered prompt with special-token parsing but no extra BOS, then sends the exact token array to native completion so another BOS cannot be inserted. `return_tokens` preserves generated IDs, including the selected EOS token in the pinned implementation. `stop_type=eos` is completed; `limit` is retained/truncated and excluded from judging. A server context-truncation flag invalidates the observation.

Generation configuration records backend, quantization, model hash/revision, embedded tokenizer/template, sampler parameters, context, build source/options and implementation identity. Hardware-specific build identity/version/binary hash are recorded per observation as runtime provenance so different Colab hardware remains auditable. Greedy decoding controls sampling, but does not promise bitwise identical arithmetic across hardware. The merger rejects different model backends or quantizations.

Python dependencies for default GGUF evaluation omit Hub/Transformers/Torch, and allow compatible Colab NumPy/Pandas versions. A stale Hub module cannot block the default native inference path. Future CircuitKIT and HF likelihood analysis must separately validate exact weights/precision, tokenizer agreement, differentiable backend compatibility and behavioral reproduction of selected quantized examples. Quantized guard judgments and answers do not establish a circuit in the fp16 model.

Native protocol verification: llama.cpp at the exact pinned commit was compiled for local CPU (GPU/Metal disabled), with unused web UI/prebuilt UI disabled. Using the publisher's TinyStories test GGUF (revision `499bc8821c6b12b4e53c5bffcb21ec206f212d81`, SHA256 `270cba1bd5109f42d03350f60406024560464db173c0e387d91f0426d3bd256d`) exercised real template, tokenization, native completion and cleanup calls. Two greedy calls returned identical IDs (54 prompt tokens, 8 generated tokens, limit stop). The server correctly caps context to a model's training context; the fixture uses 2048, while the production Aya/guard runs request 8192 and reject a differing effective context. All 116 tests passed with this native test enabled. Actual production GGUF weights/GPU inference remain untested locally.
